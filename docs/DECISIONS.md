- 2026-10-05, Paket 01: Das Beispiel in der Paketdatei („Faktor 1,5“) meint den Erwachsenenfaktor. Der Skalierungsfaktor für 20/5 → 18/5 ist 25,5 / 27,5 = 0,927. 6000 g Kartoffeln ergeben 5,6 kg, für 2/2 ergeben sie 1,1 kg. Beides ist als Test hinterlegt.
- 2026-10-05, Paket 01: Stückeinheiten sind St., Pckg., Dose, Glas, Bund. EL, TL, Prise zeigen eine Nachkommastelle ohne Endnull („2 EL“, „1,5 EL“), kg und l immer mit einer („2,0 kg“). Gerundet wird zuerst, danach umgerechnet (995 g → „1,0 kg“).
- 2026-10-05, Paket 01: Positive Mengen werden nie als 0 angezeigt. Das gilt für g und ml (mindestens 1), Stückeinheiten (mindestens 0,5, auch im Rezept, nicht nur in der Elternansicht) und EL, TL, Prise (mindestens 0,1). Das erweitert SPEC 6.
- 2026-10-05, Paket 01: Mengen ohne bekannte Einheit (leer oder unbekannt) bleiben unverändert und zeigen höchstens zwei Nachkommastellen. Sie bilden im Einkauf eine eigene Zeile (Schlüssel `<id>:`).
- 2026-10-05, Paket 01: Einkauf: Geschlossene Tage zählen nicht. Positionen mit Summe 0 (z. B. 0 Personen) entfallen. Lieferant = Lieferant der Zutat, sonst Standardlieferant der Warengruppe, sonst „Ohne Lieferant“. Fehlt die Warengruppe, heißt sie „Ohne Warengruppe“. Beide sortieren ans Ende.
- 2026-10-05, Paket 01: „Vorrat prüfen“ enthält eine Zutat nur, wenn sie in keinem Rezept des Zeitraums eine Menge hat. `aggregateShopping` bekommt Lieferanten und Warengruppen über `settings`. `toShareText` filtert nach Lieferant-ID, lässt abgehakte Schlüssel weg und enthält „Vorrat prüfen“ nicht.
- 2026-10-05, Paket 01: Allergen-Schlüssel sind `gluten`, `krebstiere`, `eier`, `fisch`, `erdnuesse`, `soja`, `milch`, `schalenfruechte`, `sellerie`, `senf`, `sesam`, `sulfite`, `lupinen`, `weichtiere`. Kurzname für Schalenfrüchte ist „Nüsse“. Ein Rezept ohne Zutaten gilt als vollständig (`complete = true`), weil die SPEC nur ungeprüfte Zutaten nennt.
- 2026-10-05, Paket 01: `templateIndexForWeek` und `applyRotation` normalisieren Start und Woche auf den Montag. Ohne Vorlagen oder ohne Startmontag gibt es keine Position beziehungsweise keine Einträge.
- 2026-10-05, Paket 02: Tabellenrechte (grant) stehen explizit in der Migration, weil „Automatically expose new tables“ im Supabase Projekt aus ist. `anon` hat auf keiner Tabelle Rechte (auch Standardrechte für künftige Tabellen sind entzogen), `authenticated` nur das, was die Policies dann einschränken. profiles und settings haben für `authenticated` nur select und update, kein insert und delete: Profile entstehen per Trigger und verschwinden mit dem Auth Nutzer, settings hat genau die eine Zeile aus dem Seed.
- 2026-10-05, Paket 02: Das Profil wird beim Anlegen des Auth Nutzers erzeugt. Rollen kommen aus `app_metadata.roles` (nur per Service Role setzbar) oder aus `user_metadata.roles`, aber nur bei Einladungen (`invited_at` gesetzt). Sonst könnte sich jemand bei offener Registrierung per `signUp` mit `roles: ["admin"]` selbst zum Admin machen. Die Auth API setzt `app_metadata` erst nach dem Insert, der Trigger sieht es über die API deshalb nicht. **Für Paket 03/04:** Nach `inviteUserByEmail` die Rollen sicherheitshalber per Service Role auf dem Profil setzen und prüfen, ob `invited_at` beim Insert schon gesetzt ist.
- 2026-10-05, Paket 02: Beschlossen mit Paul: `updated_by` (per Trigger aus `auth.uid()`, ohne Nutzer bleibt der Wert) auf settings, suppliers, ingredients, recipes, plan_days, plan_meals, week_templates. `created_by` an shopping_extras und kitchen_feedback hat den Standard `auth.uid()`. `settings.public_token` ist für alle aktiven Teamrollen lesbar.
- 2026-10-05, Paket 02: Fremdschlüssel löschen nicht mit, außer wo die SPEC `on delete cascade` nennt (recipe_ingredients, week_template_meals, shopping_checks, shopping_extras). Ein Lieferant, eine Warengruppe, ein Rezept oder eine Zutat in Benutzung lässt sich also nicht löschen, nur archivieren. `week_template_meals.recipe_id` und `rotation_entries.template_id` sind `not null`.
- 2026-10-05, Paket 02: Zusätzliche Checks gegen Unsinn: `settings.rotation_start` muss ein Montag sein, Anzahlen nicht negativ, `adult_factor` > 0, Mengen nicht negativ, `shopping_lists.days` > 0. Allergene nur die 14 Schlüssel (`allergens_valid`, ein Test gleicht sie mit `lib/allergens.ts` ab). `recipes.legacy_allergens` ist bewusst frei, weil dort die alten deutschen Namen aus dem Import stehen.
- 2026-10-05, Paket 02: RLS-Tests laufen gegen das verknüpfte Projekt (`npm run test:rls`: Vitest mit Testnutzern je Rolle, deaktiviert und anonym, danach SQL Prüfung des Profil Triggers). Sie sind nicht Teil von `npm test`, weil sie Netz und Schlüssel brauchen. Testdaten liegen im Jahr 2100 oder tragen das Präfix `__rls_`, und werden am Anfang und Ende aufgeräumt.
- 2026-10-05, Paket 02: `lib/types.ts` leitet `Course` und `AppRole` aus den DB Typen ab. Die Listen `COURSES` und `APP_ROLES` bleiben als Tupel und werden per Typprüfung gegen die DB Enums abgeglichen. Die übrigen schlanken camelCase Typen der Fachlogik bleiben unverändert.
- 2026-10-05, Paket 03: Next 16 nennt die Middleware `proxy.ts` (`middleware.ts` ist veraltet). `proxy.ts` erneuert nur die Sitzung und schickt Anfragen ohne Sitzung auf `/login`, die Rollenprüfung passiert serverseitig in `lib/auth.ts` (`requireProfile`, `requireAccess`), weil das Profil dafür aus der Datenbank kommt. Die Sitzung wird mit `getClaims()` geprüft, nicht mit `getSession()`. **Für spätere Pakete:** Öffentliche Routen stehen in `PUBLIC_PATHS` in `proxy.ts` (jetzt `/login`, `/auth/callback`). Paket 11 (`/e/[token]`, Elternansicht ohne Login), Paket 12 (falls `/druck` ohne Login) und Paket 13 (`/api/cron/daily`) müssen dort ergänzt werden.
- 2026-10-05, Paket 03: Zugriff nach Rolle: Heute, Speiseplan, Rezepte und Einkauf für alle aktiven Rollen, Vorlagen und Zutaten nur planung und admin, Admin nur admin. Gesperrte Routen leiten auf die eigene Startseite. `/zutaten` hat keinen Navigationspunkt (wie schon Paket 00). Das ist nur Komfort, die Daten schützt die RLS. Die Regeln stehen in `lib/roles.ts` mit Tests. Startseite nach Rolle: planung `/plan`, kueche `/heute`, einkauf `/einkauf`, admin `/admin`, bei mehreren Rollen in dieser Reihenfolge.
- 2026-10-05, Paket 03: „Kein Zugang“ (`/kein-zugang`) gilt für Nutzer ohne Profil, ohne Rolle und für deaktivierte Nutzer. Ein deaktivierter Nutzer sieht wegen der RLS sein eigenes Profil nicht mehr (`is_active_user()` für alle Leserechte), das wird mit abgefangen. Es war keine Migration nötig. Rollen werden bei jeder Anfrage aus der Datenbank gelesen, eine Rollenänderung wirkt also nach Neuladen, ohne neuen Login.
- 2026-10-05, Paket 03: Login: Unbekannte Adressen bekommen dieselbe Antwort „Schau in dein Postfach“ wie bekannte (Supabase meldet mit `shouldCreateUser: false` bei unbekannter Adresse 400/422). Nur zu viele Versuche (429) und unerwartete Fehler werden angezeigt. Der Hinweis „gleicher Browser und gleiches Gerät“ steht auf der Seite und in der Mailvorlage, weil der Magic Link PKCE nutzt.
- 2026-10-05, Paket 03: `/auth/callback` kann zusätzlich zum `code` auch `token_hash` + `type` einlösen (`verifyOtp`). Das braucht Paket 04 für Einladungen, und es lässt sich mit einer Mailvorlage (`{{ .SiteURL }}/auth/callback?token_hash={{ .TokenHash }}&type=email`) später nutzen, falls der Magic Link wegen PKCE zwischen Mail-App und Browser Probleme macht. Die Vorlagen in `docs/mail-vorlagen.md` nutzen vorerst `{{ .ConfirmationURL }}`.
- 2026-10-05, Paket 03: Neue Abhängigkeiten `@supabase/ssr` und `zod`, `@supabase/supabase-js` von devDependencies nach dependencies verschoben (die App braucht es zur Laufzeit). Die Sitzung hält über Cookies von `@supabase/ssr` (Standard 400 Tage Lebensdauer) mit Refresh Token Rotation.
- 2026-10-05, Paket 03: Handprüfung lief gegen das verknüpfte Projekt mit vier Wegwerf Nutzern (`__rls_p03_*`: Einkauf, Admin+Planung, inaktiv, ohne Rolle). Die Anmeldelinks kamen per Admin API (`generateLink`), es gingen keine Mails raus. Alle Nutzer sind wieder gelöscht. **Offen für Paket 04:** Nach `inviteUserByEmail` Rollen per Service Role auf dem Profil setzen (siehe Eintrag Paket 02).
